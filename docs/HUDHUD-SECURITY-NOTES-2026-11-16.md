## 1. تصحيح ملاحظة التدقيق: نطاقات 172 في neureed

**الملاحظة الأصلية** (HUDHUD-ARCHITECTURE-RESOLUTIONS-AND-FINAL-PLAN.md، القسم 2، البند 4): أن `isSafeFeedUrl` في neureed «يرفض أي `172.*` — خطأ فحص زائد».

**التحقق الفعلي** (بحث شيفرة + قراءة ملف، master بتاريخ 2026-11-16): الشيفرة الحالية في `neureed/src/lib/feed-parser.ts` صحيحة تمامًا:

```typescript
// 172.16.0.0/12
if (a === 172 && b >= 16 && b <= 31) return false;
```

تحجب `172.16.0.0/12` فقط (الخاص) وتمرر كل 172.x العام (مثل 172.56.x الخاص بمشغلي الجوال) — مطابقة تمامًا للنمط المُصحَّح في `osiris-map/src/lib/ssrf-guard.ts` المزوّد باختبارات.

**النتيجة:** لا إصلاح مطلوب في neureed. سُجّل هذا التصحيح لمنع تنفيذ عمل على مشكلة غير موجودة. ملاحظة الخطة الأصلية كانت تخص حالة شيفرة سابقة أو خطأ تدقيق — الشيفرة الموجودة اليوم على master سليمة.

**التعايش مع الخطة:** البقية من القسم 4 في الخطة المعتمدة (قرار مجموعة PostgreSQL HA واحدة PG16) لا يتأثر — لم يكن قراره معتمدًا على هذه الملاحظة.

## 2. ملاحظة تشغيلية: DATABASE_URL في سطر أوامر pg_dump

**السياق:** سكربت النسخ الاحتياطي `portal/scripts/backup-core.ts` يمرر `process.env.DATABASE_URL` كوسيط `--dbname` لعملية `pg_dump` تابعة.

**التحليل:**
- لا سر مكتوب في الشيفرة (يمر من متغير البيئة فقط) — صحيح.
- أثناء تنفيذ pg_dump، كامل connection string (بما فيه كلمة المرور) يظهر في `/proc/<pid>/cmdline` للمستخدمين على نفس المضيف القادرين على قراءة جدول العمليات.
- pg_dump يعرض هذه السلوكية عند استخدام `--dbname` مع connection string كامل (كلمة مرور مضمنة).

**التوصية التشغيلية:**
- شغّل سكربت النسخ على مضيف موثوق حيث لا يوجد مستخدمون غير موثوقين بقراءة /proc.
- البديل الأقوى عند توفر إطار تشغيلي: استخدام ملف `.pgpass` أو `PGPASSWORD` عبر بيئة العملية الفرعية (لا سطر الأوامر)، أو libpq service file — يزيل السر من جدول العمليات كليًا.
- أولوية هذا التحسين: متوسطة — ليس ثغرة في الشيفرة بل سمة بيئة تشغيل؛ يُنفّذ في مرحلة البنية التحتية (المرحلة 4/7) لا الآن.
