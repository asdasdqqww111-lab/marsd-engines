# HUDHUD Identity — تقييم zexa-auth كسلطة هوية مركزية

**التاريخ:** 2026-11-16
**النطاق:** تقييم تقني مبني على الشيفرة الفعلية للمستودع (لا افتراضات تشغيلية).
**القاعدة:** لا فرض SSO إلزامي في الإنتاج — التكامل اختياري تدريجي.

## ما تم التحقق منه فعليًا في zexa-auth

من فحص الشيفرة وملفات التهيئة في المستودع:

| البند | الحالة الفعلية | الدليل |
|---|---|---|
| إطار المصادقة | Better Auth (نفس إطار البوابة) | `zexa-auth/package.json` (better-auth) |
| قاعدة البيانات | PostgreSQL عبر Drizzle ORM مع ترحيلات | `zexa-auth/drizzle/` + drizzle.config.ts |
| إدارة المستخدمين | لوحة إدارة كاملة: أدوار، حظر، جلسات، تحقق بريد | README + `src/app/admin/` |
| مزودو OAuth الحاليون | Google + GitHub فقط | `.env.example` (GOOGLE_CLIENT_ID/SECRET, GITHUB_CLIENT_ID/SECRET) |
| البريد | Resend للتحقق والإشعارات | `.env.example` (RESEND_API_KEY) |
| RBAC التطبيق | دوران (admin/user) عبر admin plugin | README + شيفرة admin |
| **OIDC provider (إصدار رموز لتطبيقات أخرى)** | **غير مُهيَّأ حاليًا** | لا متغيرات OIDC issuer/keys في .env.example |

## الاستنتاج الصادق

1. **zexa-auth جاهز كمصادقة تطبيق** (login لمنظومة HUDHUD Identity نفسها) — يعمل اليوم كتطبيق مستقل كامل.
2. **zexa-auth ليس بعد سلطة هوية مركزية (IdP)**: لا يوجد تكوين OIDC/OAuth2 provider حاليًا. Better Auth يدعم إضافة OIDC plugin، لكن هذا **تغيير تهيئة غير منفَّذ** — لا يُدَّعى أنه جاهز.
3. **البوابة (CONTROL) مصادقة محلية مستقلة** عن قصد: email/password + disableSignUp + مشغلون عبر seed فقط. هذا قرار معماري صحيح للمرحلة الحالية (لوحة تحكم لا تعتمد على أي تطبيق — تعطل zexa لا يقفل المشغلين خارج البوابة).

## المسار التطبيقي المقترح (دون SSO إلزامي)

### المرحلة أ — تمكين zexa كـ IdP (عمل في zexa-auth نفسه)
1. إضافة Better Auth OIDC provider plugin (تغيير شيفرة zexa-auth — مشروع مستقل بفرع خاص).
2. متغيرات بيئة جديدة: مفاتيح توقيع OIDC + issuer URL + أزواج client لكل تطبيق مستهلك.
3. نشر zexa-auth في الإنتاج مع TLS (شرط مسبق لكل OAuth flows).

### المرحلة ب — استهلاك اختياري من البوابة
1. إضافة Better Auth genericOAuth plugin في البوابة كخيار دخول ثانٍ بجانب email/password (المحلي يبقى — لا SSO إلزامي).
2. إنشاء client credentials للبوابة في zexa (client_id/secret عبر secret manager — لا تلتزم أبدًا).
3. ربط callback URL: `https://<portal>/api/auth/oauth2/callback/<zexa>`.
4. سياسة: المشغلون الجدد عبر OIDC يدخلون بدور viewer افتراضيًا — الترقية لأدوار أعلى تتم عبر admin فقط (نفس مبدأ أقل امتياز الحالي).

### المرحلة ج — استهلاك تدريجي من التطبيقات
لكل تطبيق (neureed, nchat, rhex-forum, umami...) قرار مستقل حسب جدواه:
- التطبيقات ذات مصادقة قائمة تعمل: لا تُكسر — يُضاف الدخول بـ HUDHUD Identity كخيار فقط.
- التطبيقات الجديدة: تعتمده من البداية.
- أعمار الجلسات والموافقات (consent) تُدار مركزيًا في zexa.

## الضوابط الأمنية (غير قابلة للتفاوض)

- **عزل القواعد**: قاعدة zexa مستقلة تمامًا؛ لا مشاركة قاعدة بين zexa والبوابة أو التطبيقات.
- **الأسرار**: كل مفاتيح OIDC وclient secrets عبر secret manager — لا تلتزم في Git (يغطيها .gitignore الحالي).
- **الجلسات**: cookies منفصلة لكل نطاق؛ لا رمز يعبر تطبيقات بلا تحقق توقيع.
- **التراجع**: تعطيل خيار OIDC في البوابة يعيدها للمصادقة المحلية فورًا دون فقدان وصول المشغلين (لأن المحلي لم يُزل).
- **الإقفال**: تفعيل أي SSO إلزامي = عملية قد تقفل مستخدمين → تتطلب موافقة صريحة منفصلة وفق سياسة الموافقات. هذا التقييم لا يفعّل شيئًا منها.

## ما يتطلبه التنفيذ الفعلي (خارج قدرة الشيفرة وحدها)

1. نشر zexa-auth في الإنتاج مع TLS وDNS — قرار موارد وموافقة إنتاج.
2. قرار تشغيل OIDC issuer (نطاق فرعي مثل identity.hudhud...) — قرار DNS/إنتاج.
3. تنفيذ المرحلة أ كفرع عمل منفصل في zexa-auth + مراجعة + دمج بموافقة.
4. اختبارات تكامل فعلية (login عبر OIDC end-to-end) — تتطلب بيئة staging.

## الخلاصة

- **اليوم**: البوابة مستقلة وآمنة بمصادقتها المحلية — لا اعتماد تشغيلي على أي تطبيق. ✅
- **zexa-auth**: مؤهل تقنيًا (Better Auth) لكن يحتاج عمل تهيئة OIDC ليصبح سلطة هوية. ⏳ عمل مستقبلي بفرع خاص.
- **SSO الإلزامي**: مرفوض في هذه المرحلة — التكامل اختياري فقط مع إبقاء المسارات المحلية.
