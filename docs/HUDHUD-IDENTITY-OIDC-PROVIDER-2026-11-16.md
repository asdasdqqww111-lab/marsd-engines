## الحالة: منفّذ (شيفرة) — بانتظار الفحص التشغيلي في staging

## ما نُفِّذ فعليًا في هذه المرحلة

| # | التغيير | الملف | النوع |
|---|---------|-------|------|
| 1 | إضافة `oidcProvider` + `jwt` (JWKS) من Better Auth plugins خلف مفتاح تشغيل `HUDHUD_IDENTITY_ENABLED` | `zexa-auth/src/lib/auth.ts` | ميزة هوية |
| 2 | تحميل عملاء OIDC من متغير البيئة `HUDHUD_OIDC_CLIENTS` (JSON) مع تحقق صارم من الصيغة وفشل مسموع في السجلات دون كشف أسرار | `zexa-auth/src/lib/auth.ts` | أمن |
| 3 | إضافة البادئة `/api/oidc/` للمسارات العامة (discovery/authorize/token/userinfo/JWKS يجب أن تكون متاحة للأطراف المعتمدة بلا جلسة — إلزامية في مواصفة OIDC؛ التفويض نفسه يتطلب مصادقة المستخدم النهائي) | `zexa-auth/src/lib/public-paths.ts` | أمن |
| 4 | توثيق متغيرات HUDHUD_IDENTITY_* الثلاثة في قالب البيئة (معطّلة افتراضيًا — تعليقات فقط) | `zexa-auth/.env.example` | توثيق |

## حدود التصميم المحفوظة

- **دون تشغيل HUDHUD_IDENTITY_ENABLED=true**: لا يُحمّل أي plugin جديد — zexa-auth يعمل **بالتطابق التام** مع الوضع السابق (جلسات محلية، دخول اجتماعي، admin). لا كسر لأي وظيفة قائمة.
- **لا SSO إلزامي**: التفعيل الإنتاجي يفرض موافقة صريحة منفصلة وفق سياسة الموافقات؛ staging أولًا.
- **الأسرار**: لا client secret في الشيفرة ولا في المستودع أبدًا — البيئة (secret store للمشغل) هي المصدر الوحيد. تمرير تالف يُسجّل خطأً صريحًا ويُرجع قائمة فارغة (فشل آمن: لا عملاء، لا استجابة OIDC).
- **JWT/JWKS**: RS256 بمفاتيح غير متماثلة — التطبيقات المعتمدة تتحقق من التوكنات عبر JWKS العام دون مشاركة أي سر توقيع.

## ما يتطلبه التشغيل في staging (خطوات المشغل)

1. `npm install` في zexa-auth (better-auth ^1.6.11 موجود مسبقًا؛ لا اعتماد جديد).
2. ضبط `HUDHUD_IDENTITY_ENABLED=true` و`HUDHUD_OIDC_ISSUER` و`HUDHUD_OIDC_CLIENTS` من secret store في بيئة staging فقط.
3. تشغيل `npm run db:push` — plugins OIDC/JWT تنشئ جداولها (oidc_* وjwks) عبر آلية Better Auth التلقائية.
4. التحقق الفعلي: `GET /api/oidc/.well-known/openid-configuration` ثم تدفق authorize بالكامل مع PKCE مع عميل تجريبي واحد.

## الأثر الأمني

- إيجابي: مركزية الهوية تصبح ممكنة مع مفاتيح RS256 قابلة للتدوير، وبدون مفاتيح مشتركة بين التطبيقات.
- نقطة انتباه للمشغل: `/api/oidc/` عام للوصول الشبكي لكن كل مسار داخله يفرض متطلباته (authorize يتطلب جلسة، token يتطلب client credentials، userinfo يتطلب access token صالح).

## التالي

1. مراجعة هذا التغيير ودمجه بموافقة صريحة (لا يغيّر أي سلوك افتراضي — الدمج آمن وظيفيًا لأن كل الجديد معطّل افتراضيًا).
2. تشغيل الفحوصات يدويًا في zexa-auth قبل الدمج: `npm run build`.
3. نشر staging + التحقق الفعلي لتدفق OIDC (discovery → PKCE → token → JWKS → revocation).
4. المرحلة ب (ربط مُدار للتطبيقات) تُفتح فقط بعد نجاح الفحص الفعلي في staging وبموافقة منفصلة.
